# 11. 읽기 카드 오답 보기 — 측정과 개선

작성 2026-11-14 · 대상 코드 `src/distractors.ts` · 측정 도구 `scripts/distractor-report.mjs`, `scripts/distractor-bench.mjs`

## 0. 결론

- **이전 생성기는 읽기를 몰라도 64%를 맞힐 수 있었다**(우연 25%). 가장 큰 단서는 "정답이 보기들의 한가운데에 있다"였다. 오답이 모두 정답에서 한 글자씩 바꾼 변형이라, 나머지 셋과 가장 가까운 보기를 고르기만 해도 91%가 맞았다. 길이가 혼자 다른 보기가 67% 카드에 있었고, 1모라 단어(九 く, 五 ご)는 오답의 68%가 길이부터 달랐다(はね, かつ).
- **새 생성기에서는 같은 얕은 단서를 모두 써도 28%**로 우연과 거의 같다. 오답 길이 불일치 35.4% → 0.1%, 길이로 보기 하나가 튀는 카드 67.4% → 0%, 음독 꼴이 아닌 오답 20.5% → 0.1%, "정답이 한가운데" 84.7% → 0.0%, 사전에 실린 같은 단어의 다른 읽기를 오답으로 낸 경우 143 → 0.
- 오답은 **한국인이 실제로 헷갈릴 읽기**에서 고른다. 한자마다 같은·비슷한 한국 한자음을 가진 한자의 읽기(都 도 → 度 ど·古 こ·保 ほ, 二 이 → 利 り·異 い·耳 じ), 같은 한자의 다른 음, 장음·탁음·っ·ん·きょう/こう 같은 근접음이다.
- **대체(fallback)**: 좋은 오답이 2개뿐이면 보기 3개, 1개 이하면 그 카드는 보통 뜻 카드처럼(떠올리고 정답 보기) 묻는다. **배포 데이터 3,489단어 중 둘 다 0개**다.
- **비용**: 데이터에 `x` 열(사전의 다른 읽기, 550단어)을 붙여 n*.json 합계 +10.8KB(gzip +4.8KB), JS +6.1KB(gzip +2.5KB). 카드당 시간은 중앙값 4.1ms → 0.6ms, 최악 11.4ms → 3.1ms로 오히려 빨라졌고, 세션 첫 읽기 카드에서 한 번 색인을 만드는 데 약 30~60ms(데스크톱)가 든다.

## 1. 측정 방법

`node --experimental-strip-types scripts/distractor-report.mjs [--gen <생성기 .ts>] [--seeds 5] [--show <cue>]`

- 대상: 5개 급수의 `k === 'S'` 단어 3,489개 전부 × 보여 주기 5번(시드 `<id>:r|0..4`, 앱과 같은 형식) = 17,445장.
- 이전 생성기는 `git show 7e598d9:src/distractors.ts`를 `--gen`으로 넘겨 같은 잣대로 쟀다.
- 잣대는 생성기와 독립이다.
  - **음독 꼴**: 음독 단어(`rt === 'on'`)의 보기가 KANJIDIC2 음독(연탁·촉음 변형 포함, `data/hanja/kanji.tsv`)으로 한자 수만큼 잘리는가. 훈독 단어는 일본어로 가능한 꼴인지(`plausible`)만 본다.
  - **같은 단어의 다른 읽기**: 같은 표기의 다른 항목 + JMdict가 그 표기에 주는 모든 읽기(`data/readings/`, §5).
  - **한국 한자음 규칙**: `src/sound.ts`의 받침 대응(ㄴ·ㅁ→ん, ㅇ→う·い, ㄱ→く·き, ㄹ→つ·ち, ㅂ→う, 받침 없음→그 어느 것도 아님, 동화된 っ 허용). 정답이 규칙에 맞는 카드에서 "규칙에 맞는 보기가 정답 하나뿐"인 비율.
  - **한가운데**: 편집 거리 합이 가장 작은 보기가 정답 하나뿐인 비율.
  - **얕은 단서 풀이기**: 음독 꼴이 아닌 보기 → 한자음 규칙에 안 맞는 보기 → 혼자 다른 길이를 차례로 지우고, 남은 것 중 한가운데를 고르는 학습자의 기대 정답률. 우연은 1/보기 수.
  - **실제 단어 단서**(참고): 보기 중 데이터에 있는 단어의 읽기가 정답 하나뿐인 비율. 학습자가 그 단어를 들어 본 적이 있어야 쓸 수 있는 단서라 풀이기에는 넣지 않고 따로 적었다.
- 길이는 모라로 센다(きょう = 2, がっこう = 4).

**원인**
1. 오답 셋 중 둘이 정답의 한 단계 변형(장음·탁음·っ·ゃ)이고 서로는 두 단계 떨어져 있어, 정답이 늘 한가운데였다.
2. 나머지 하나는 "같은 급수에서 비슷한 길이의 단어"였는데, 짧은 단어(3모라 이하)는 길이가 같아야만 해서 후보가 고유어로 채워졌다(九 く → ちか·はね, 胃 い → がわ·たま). 음독 단어에 훈독 고유어가 섞이면 꼴만 보고 지울 수 있다.
3. 장음 변형이 모라 수를 바꿔서, 길이가 혼자 다른 보기가 생겼다(さんぎょう / さんぎょ).
4. ゃ ↔ や 변형(ちゆう, じよし)은 오자처럼 보여 바로 지워진다(19.3%).
5. 같은 표기의 다른 항목만 정답으로 봤기 때문에, 사전이 인정하는 다른 읽기(重複 じゅうふく 등)가 143번 오답으로 나갔다.
6. 카드마다 8,130단어 전체를 훑어 4ms 안팎이 걸렸다.

## 3. 새 생성기

`readingQuestion(word, pool, seed): ReadingQuestion | null` — 시드 계약은 그대로(`<카드 id>|<reps>`): 같은 보여 주기는 다시 그려도·되돌려도 같은 보기·같은 순서, 다음 복습은 새 조합.

**색인 (불러온 데이터에서 실행 중에 만든다, 풀(pool) 배열마다 한 번)**
- 데이터의 읽기 분할 열 `a`(3,814단어)에서: 한자 → 그 한자의 음 조각, 한국 한자음 음절(`sk`의 한 글자) → 그 음절로 읽히는 한자들의 음 조각, 데이터에 나오는 모든 음 조각.
- 표기 → 항목, 한자 → 그 한자를 쓰는 단어, 급수·모라 수 → 읽기, 모든 읽기(실제 단어 여부).
- 별도 한자 음 파일은 만들지 않았다. 분할 열만으로 1모라 단어까지 충분한 후보가 나왔다(대체 0).

**후보**
1. 한자별 조각 바꾸기(분할을 아는 단어; 분할 열이 없는 음독 단어는 실행 중에 같은 조각으로 다시 잘라 본다. 計画 けいかく처럼 데이터 읽기에 する가 붙은 N4 19단어는 する를 떼고 묻고 보기마다 다시 붙인다):
   - 같은 한국 한자음 한자의 음(産 산 → 散·算 さん, 業 업 → ぎょう), 한 소리 다른 한국 한자음(받침만 다름 > 초성만 > 모음만: 도 → 동 どう, 독 どく / 고 こ, 보 ほ / 두 ず). 두음법칙으로 생긴 혼동(리 ↔ 이: 理科 りか → いか)도 데이터에서 그대로 나온다.
   - 같은 한자의 다른 음(2자 이상 단어만. 한 글자 단어는 그 한자의 다른 음이 곧 그 단어의 다른 읽기일 수 있어서 쓰지 않는다: 気 け).
   - 조각의 근접음: 탁음·반탁음, 장단음, きょう ↔ こう ↔ きゅう, ん 붙이기·빼기, 동화된 っ ↔ く·き·つ·ち. 바꾼 조각은 데이터에 실제로 있는 음 조각이어야 한다.
   - 두 조각을 동시에 바꾼 것도 후보로 둔다. 그래서 (さん|ぎょう)에 대해 (ざん|ぎょう), (さん|しょう), (ざん|しょう)처럼 오답끼리도 가까운 2×2 묶음이 생기고, 정답이 더는 한가운데가 아니다.
2. 읽기 전체의 소리 변형(기존 규칙). 분할이 없는 단어(훈독 등)는 변형의 변형까지.
3. 실제 단어의 읽기: 같은 한자를 쓰는 다른 단어, 같은 급수·같은 모라 수의 단어(첫 글자·끝 글자·읽기 유형이 같을수록 우선).

**거르기 (하나라도 걸리면 후보 아님)**: 일본어로 불가능한 꼴, 정답과 같은 소리(ぢ/じ, おう/おお 등) 또는 언뜻 같은 꼴(작은 ゃゅょっ), 이 단어의 맞는 읽기(자기 읽기들, 같은 표기의 다른 항목, `x` 열의 사전 읽기, 한 글자 단어면 그 한자의 모든 음), 정답과 2모라 이상 차이, 음독 단어인데 데이터의 음 조각으로 한자 수만큼 잘리지 않음.

**고르기**: 점수 상위 12개 후보에서 가능한 세 개 조합을 모두 따져 가장 좋은 묶음을 고른다(220가지).
- 개별 점수: 출처(같은·가까운 한국 한자음 > 근접음 > 실제 단어), 데이터에서 그 조각이 쓰인 빈도, 정답과 같은 길이(+2), 정답이 한자음 규칙에 맞으면 규칙에 맞는 후보(+), 실제 단어(+), 시드에 따른 작은 흔들림(보여 줄 때마다 다른 조합).
- 묶음 점수: 길이가 모두 같거나 2개·2개(+4, 아니면 −4), 정답이 한가운데면 −3, 정답만 한자음 규칙에 맞으면 −2.5, 실제 단어 오답이 가능한데 하나도 없으면 −1.5, 출처가 다양하면 조금 +.

## 4. 대체 규칙 (guard rail)

- 좋은 오답(§3의 거르기를 통과한 후보)이 **3개 이상**: 보기 4개.
- **2개**: 보기 3개(`MIN_WRONG = 2`). 화면은 같은 2열 격자에 버튼 3개, 숫자 키는 1–3만 받는다.
- **1개 이하**: `null`을 돌려주고, 학습 화면은 그 읽기 카드를 보통 뜻 카드처럼 보여 준다(앞면은 한자와 "읽기" 표시, "모르겠어요 / 정답 보기" → 읽기·뜻 공개 → 모르겠어요·알아요·쉬워요). 카드 id와 FSRS 기록은 읽기 카드 그대로다. 정답을 알려 주는 자동 발음은 정답을 본 뒤에만 나온다.
- 모자란 칸을 아무 읽기로 채우는 이전의 마지막 단계("아무 단어나 길이 가까운 것")는 없앴다.
- **배포 데이터에서 걸리는 단어**: 보기 3개 0개, 뜻 카드 대체 0개(3,489단어 × 5회 모두 4개). 단위 테스트가 이 수를 계속 확인한다. 대체 동작 자체는 작은 가짜 데이터로 테스트한다(胃 い 혼자 → null, 派 は 혼자 → は·ば·ぱ 3개).

## 5. 데이터에 더한 것: `x` 열

- 오답이 "같은 단어의 다른 유효 읽기"가 되면 안 된다. 같은 표기의 다른 항목만으로는 모자라서(이전 143건), JMdict(jamdict-data 1.5, EDRDG CC BY-SA)에서 S 단어 표기의 모든 읽기를 뽑아 데이터에 없는 것만 `data/readings/n{l}.json`에 두고(`scripts/enrich/alt-readings.py`), `build-data.mjs --extras`가 12번째 열 `x`로 붙인다(공백 구분, 예: 重複 → `じゅうふく`, 今日 きょう → `こんにち こんち こんじつ`). S 단어 550개에만 있다.
- 크기: n*.json 합계 788,869 → 799,667바이트(+10.8KB, +1.4%), gzip −9 기준 +4.8KB. 앞 4열·행 순서·단어 id는 그대로다(`tests/unit/data.test.ts` sha256 통과, 기존 열도 바이트 단위로 같음을 따로 확인).
- `public/data/NOTICE.txt`에 `x` 열의 출처(JMdict, CC BY-SA)를 적었다.
- 다시 만들기: `scripts/enrich/fetch-sources.sh`(jamdict.db 캐시) → `python3 -I scripts/enrich/alt-readings.py` → `npm run data`.

**읽는 법과 남은 약점**
- 길이·한가운데·한자음 규칙은 고르기 단계가 직접 피하는 단서라, 그 열이 0에 가까운 것은 설계대로 된 것이다. 잣대가 생성기와 독립이라는 점(KANJIDIC2 전체 음독, JMdict)만 따로 확인할 가치가 있다: "음독 꼴 아님 0.1%", "다른 유효 읽기 0"이 그 확인이다.
- **실제 단어 단서**는 남았다(44.7%, 이전과 비슷). 오답 대부분이 실제 단어가 아닌 음 조합이라, 학습자가 정답 단어를 들어 본 적이 있으면 "익숙한 것"을 고를 수 있다. 특히 5모라 이상(3자 한자어)은 같은 길이의 실제 단어 오답을 찾기 어려워 70%가 "정답만 실제 단어"다. JLPT 漢字読み 문제도 대부분 비단어 오답(しょうかい / しょかい / しょうがい)이라 시험과 같은 성격이지만, 줄이려면 같은 한국 한자음의 실제 단어를 더 적극적으로 끌어와야 한다.
- 1모라 단어는 3.1%의 오답이 2모라다(1모라 후보가 모자랄 때 길이를 2개·2개로 맞춘 경우: 種 しゅ → しょ·しゅう·じゅう).
- 음독이 아닌 S 단어(훈독 111, 혼합 35, 불규칙 29 — 兄 あに, 魂 たましい 등)는 한국 한자음이 도움이 되지 않아 소리 변형과 같은 길이 단어에서 고른다. 이 묶음의 오답은 "그럴듯한 다른 일본어 단어" 수준이다(前 まえ → いえ·いけ·まど).
- 1모라 음독 단어에서 오답 셋이 모두 다른 한자 하나의 음이므로, 한자를 잘 아는 학습자에게는 "그 음은 다른 한자"라는 지식이 필요하다 — 이것은 의도한 난이도다.
