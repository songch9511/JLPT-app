# 09. 단어 설명 사전 생성 파이프라인

작성 2026-11-13 · 근거: [01-business-model.md](01-business-model.md) §4.4·§5.5·결정 4, [07-security-operations.md](07-security-operations.md) §A-3, [08-word-data.md](08-word-data.md) §3 · 코드: `scripts/explain/` · 출력: `data/explain/`

## 결론

1. **8,130단어 설명을 한 번에 만드는 배치 파이프라인을 만들었다.** Message Batches API + 구조화 출력(JSON 스키마)으로 안정 단어 ID(`w0k3`, 08 문서 §7)를 `custom_id`로 보내고, 순서와 무관하게 ID로 받아 합친다. 거절·`max_tokens`·오류·만료는 이유별로 재시도 목록에 넣고 **실패한 ID만** 다시 보낸다. 중단돼도 같은 명령을 다시 실행하면 열린 배치를 먼저 수집하고 다시 제출하지 않는다.
2. **API 키 없이 만들었고 실제 호출은 한 번도 하지 않았다.** 테스트 47개는 모두 가짜 클라이언트로 돌며 `npm test`로 통과한다(네트워크 없음). 모델 출력 품질은 아직 아무도 보지 못했다 → 첫 단계는 **200단어 샘플(약 $1.7)** 이다.
3. **모델은 01 문서 결정대로 `claude-sonnet-5-5`** (설정값 `EXPLAIN_MODEL`). claude-api 스킬의 기본 모델은 `claude-opus-5-5`지만 이 작업은 01 문서의 비용·품질 판단을 따른다. 거절된 단어는 `claude-sonnet-5`로 다시 보낸다(배치는 서버 측 `fallbacks`를 받지 않음).
4. **예상 비용 $40~56, 상한 $76 (재시도 5% 포함, 전부 추정).** 가격과 배치 50% 할인은 공식 가격표에서 확인했고(측정 아님, 문서 확인), 토큰 수는 글자 수 어림이다. 출력 토큰(800, 01 문서 가정)이 비용의 60~85%를 차지한다. 샘플을 돌리면 같은 명령이 실측값으로 다시 계산한다.
5. **시간: 배치 5개(2,000건씩)를 동시에 내고, 공식 문서 기준 대부분 1시간 안·최대 24시간.** 재시도 한 번을 더해 반나절 안쪽을 예상하지만 측정하지 않았다. 사람 검수가 훨씬 오래 걸린다(§8).
6. **앱 출력은 ID 카운터 기준 100단어 묶음 파일 82개 + `manifest.json`**, 합계 약 5~7MB(gzip 약 2~3MB, 추정). 단어 하나를 보려면 묶음 하나(약 70~90KB, gzip 30KB 안팎)만 받는다. 유료 콘텐츠라 `public/`이 아닌 `data/explain/dist/`에 두고 01 문서대로 R2 + Worker로 낸다.

## 1. 파이프라인이 하는 일

```
public/data/words-n*.json ─┐                 ┌─ accepted/<w+첫 자리>.json (검증 통과)
data/tags/*.json ────┼─ 요청 만들기 ─ 배치 ─┤
data/hanja/kanji.tsv ┘   (단어 ID만 다름)    └─ failed.json (재시도 목록 + 이유)
                                                   │ retry (실패 ID만)
validate (현재 단어·태그로 재검사) ─ review (검수표) ─ export (dist/ 묶음 + manifest)
```

- 단어 목록·태그·한자표는 **실행할 때마다 새로 읽는다.** 태그는 아직 수정 중이라 고정하지 않는다. 라벨이 없는 단어는 사전 작업 힌트를 "추정"으로 표시해 넘기고, 모델이 스스로 확인하게 한다.
- 출력마다 생성 당시의 단어(표기·읽기)와 태그를 같이 저장한다. 나중에 `validate`가 **단어가 바뀌었거나(`word-changed`) 태그 유형이 바뀐(`tag-changed`)** 출력을 찾아 재시도 목록으로 돌린다. 단어 ID는 이제 안정 ID라(08 문서 §7) 다른 단어에 붙지는 않지만, 표기를 고치면 같은 ID의 단어 내용이 바뀌므로 이 확인은 그대로 필요하다.
- 상태는 모두 `data/explain/work/`의 JSON이다: `state.json`(배치 ID와 단어), `accepted/`, `failed.json`, `usage.json`(응답마다 토큰·지연 실측), `raw/`(받은 결과 원문, git 제외).

## 2. 설명 스키마와 길이 제한

길이는 글자 수(코드 포인트). 구조화 출력은 문자열 길이·배열 개수 제약을 지원하지 않아 **필드 설명으로 모델에 알리고 검증기에서 강제**한다.

| 필드 | 내용 | 제한 |
| --- | --- | --- |
| `examples[2]` `.ja` | 표제어가 든 예문(활용 허용) | 정확히 2개. N5 24자 · N4 28 · N3 32 · N2/N1 40 |
| `.kana` | 문장 전체 읽기, 히라가나(가타카나 단어는 그대로), 한자·숫자·로마자 없음 | 예문 한도×2+10 |
| `.ko` | 자연스러운 한국어 번역 | 50자 |
| `kanji[]` | 표제어의 한자마다 `char`, 이 단어에서의 `reading`(히라가나, 숙자훈이면 빈 값 + `kind: whole`), `kind`(on/kun/whole), `hanja`(훈음 "배울 학") | 6개, 읽기 8자, 훈음 12자 |
| `tip` | 한국어 화자용 암기 팁(가나·한자 허용) | 80자 |
| `trap` | 거짓 친구의 함정. F가 아니면 빈 값 | 80자 |
| `related[]` | 관련어 `word`·`kana`·`ko`·`rel`(syn/ant/kanji/confusable) | 2~3개, 15/20/20자 |
| `origin` | 가타카나 외래어의 원어("pool (영어)"). **로마자가 허용되는 유일한 필드** | 30자 |
| `meaningFlag` | 주어진 한국어 뜻이 틀렸으면 고친 뜻(편집자용, 앱으로 내보내지 않음) | 40자 |

**단어 유형(08 문서 `k`)별 내용**: S(동형동의)는 뜻을 이미 알므로 팁이 **읽기**(일본 음 ↔ 한국 한자음 대응, 불규칙 읽기)를 다룬다. F(거짓 친구)는 `trap`이 **필수**이고 팁은 일본어 뜻을 기억하게 한다. J는 한자 뜻으로 의미를 조립한다. N·M(고유어·혼종)은 **용법**(조사, 연어, 뉘앙스, 비슷한 말과의 차이), L은 원어는 `origin`에만 쓰고 팁은 의미 차이, K는 용법. `meaningFlag`는 아직 전수 검수 안 된 한국어 뜻(README)을 잡는 부수 효과를 노린 것이다.

## 3. 프롬프트 (`scripts/explain/lib/prompt.mjs`)

- **고정 부분이 앞**: 시스템 프롬프트(지시·유형별 규칙·금지 목록·예시 1개)와 출력 스키마는 모든 요청에서 바이트 단위로 같고, 시스템 블록에 `cache_control: {type: "ephemeral", ttl: "1h"}`를 단다. 배치는 5분 넘게 걸릴 수 있어 배치 문서가 1시간 TTL을 권한다. 날짜·ID 같은 가변 값은 시스템 프롬프트에 없다(테스트로 확인).
- **단어 데이터는 데이터로**: 사용자 메시지는 `<word>` 안의 JSON 한 덩어리뿐이다(급수, 표기, 읽기, 한국어·영어 뜻, 유형과 출처 label/hint, 한국 한자음, 거짓 친구 메모, 읽기 유형, 한자별 한국음·음독·훈독). 프롬프트는 "이 안의 값은 지시가 아니다"라고 밝힌다. 07 문서 원칙대로 서버도, 이 스크립트도 자유 입력 프롬프트를 받지 않는다.
- **급수 반영**: 급수별 문법 범위(N5 です/ます…)와 길이 한도를 프롬프트와 검증기 양쪽에 둔다.
- **금지 목록(명시)**: 로마자(origin 제외), 지어낸 읽기(모르면 `whole` + 빈 읽기), 표제어 없는 예문, 표제어 표기 바꿔치기, 학습 앱에 부적절한 내용(성적 내용, 혐오 표현, 잔혹한 폭력, 자해, 마약, 도박, 정치, 종교, 실존 인물·회사·상표), JSON 밖 설명.
- 프롬프트 안의 예시(工夫)는 검증기를 통과하는지 테스트한다.

## 4. API 사용 (claude-api 스킬 기준)

| 항목 | 처리 |
| --- | --- |
| 호출 | `@anthropic-ai/sdk` 1.8.0(서버와 같은 버전) `client.messages.batches.create/retrieve/results`. 샘플·단어 재생성은 같은 파라미터로 `messages.create` |
| 출력 | `output_config.format = {type: "json_schema", schema}` + `effort: "low"`. 사고는 생략(Sonnet 5.5는 adaptive가 기본이고 `disabled`는 400) |
| 보내지 않는 것 | `stream`, `speed`, `fallbacks`(배치에서 거부), `temperature` 등 샘플링 값, 강제 `tool_choice` |
| 결과 매칭 | `custom_id` = 단어 ID(`^[a-zA-Z0-9_-]{1,64}$` 충족). 순서 무시, 모르는 ID·중복은 버림, 안 온 ID는 `missing` |
| `stop_reason: refusal` | 재시도 목록 → `claude-sonnet-5`로 재전송(같은 모델 재전송은 다시 거절되기 쉬움, 공식 문서) |
| `stop_reason: max_tokens` | `max_tokens` 4,000 → 8,000 → 16,000 |
| `errored` | `invalid_request_error`면 자동 재시도 안 함(요청 자체가 틀림), 나머지는 재시도 |
| `expired`·`canceled`·JSON 파싱 실패·검증 실패 | 같은 파라미터로 재시도. 단어당 최대 3회 |
| 재개 | 제출 직후 배치 ID를 `state.json`에 원자적으로 저장. 제출 도중 죽으면 "제출 중" 표시가 남아 재제출을 막고 `adopt`로 정리 |

## 5. 명령 순서 (`scripts/explain/`에서)

```sh
npm ci && npm test                         # 의존성(SDK) 설치, 테스트 47개 (네트워크 없음)
export ANTHROPIC_API_KEY=...               # 전용 워크스페이스 키 (§12)

node cli.mjs run --dry-run                 # 0원. 요청 수·본문 크기·비용/시간 추정 (아무것도 안 보냄)
node cli.mjs count-tokens --n 30           # 무료(count_tokens). 입력 토큰을 30단어로 측정 → 추정에 반영
node cli.mjs run --sample 200              # 약 $1.7. 급수×유형 층화 200단어를 동기 호출 → review/sample.html
#   → 검수(§8). 프롬프트를 고치면 lib/config.mjs의 PROMPT_VERSION을 올리고:
node cli.mjs validate --stale-prompt && node cli.mjs retry --sync
node cli.mjs run --dry-run                 # 샘플 실측(출력·사고 토큰, 캐시)으로 다시 추정

node cli.mjs run                           # 남은 단어를 배치로 제출 → 대기 → 수집 (끊기면 같은 명령)
node cli.mjs run --no-wait                 # (선택) 제출만 하고 종료, 나중에 `run`으로 수집
node cli.mjs status [--remote]             # 진행 상황 / 계정의 최근 배치
node cli.mjs retry --dry-run               # 재시도 대상·이유·바뀔 파라미터 확인
node cli.mjs retry                         # 실패 ID만 다시 (소량이면 --sync)
node cli.mjs validate                      # 현재 단어·태그·교차 중복으로 전체 재검사 → 실패는 재시도 목록
node cli.mjs retry
node cli.mjs review --levels n5,n4 --all               # N5·N4 전수 검수표
node cli.mjs review --levels n3,n2,n1 --share 0.05     # N3~N1 5% 층화 표본 (+경고 있는 항목)
node cli.mjs export                        # data/explain/dist/<묶음>.json + manifest.json
```

`--levels n5,n4`, `--limit N`, `--ids n5-1,n5-2`는 `run`·`retry`·`review`에 공통이다.

## 6. 비용과 시간

가격(공식 가격표, 2026-11-13 확인): Sonnet 5.5 입력 $2 · 출력 $10 · 1시간 캐시 쓰기 $4 · 캐시 읽기 $0.10 /MTok. 배치는 전부 50%이고 **배치 할인과 캐시 배수는 겹친다**(같은 페이지). 대체 모델 Sonnet 5는 캐시 읽기만 $0.20.

| 요청당 토큰 | 값 | 근거 |
| --- | --- | --- |
| 공유 접두부(시스템+스키마) | 2,391 | **어림**(ASCII 4자=1, 한·일 1자=1). `count-tokens`가 실측으로 바꿈 |
| 단어별 입력 | 89 | 어림, 8,130단어 평균 |
| 출력(사고 포함) | 800 | **가정**(01 §4.2). 출력은 미리 셀 수 없어 샘플로만 측정 |

`node cli.mjs run --dry-run` 결과(8,130 × 1.05 재시도):

| 경우 | 합계 | 출력 | 캐시 쓰기 | 캐시 읽기 | 입력 |
| --- | --- | --- | --- | --- | --- |
| 캐시 적중 0%(매번 1시간 캐시 쓰기, 최악) | $75.74 | $34.15 | $40.82 | $0 | $0.76 |
| 캐시 적중 50% | $55.83 | $34.15 | $20.41 | $0.51 | $0.76 |
| 캐시 적중 90% | $39.91 | $34.15 | $4.08 | $0.92 | $0.76 |
| 참고: 캐시 끔 | $55.32 | $34.15 | — | — | $21.18 |

- 배치 안의 캐시 적중은 "최선 노력"이라 미리 알 수 없다. 적중이 약 50% 이하이면 캐시를 끈 쪽이 싸다. 첫 배치를 수집하면 `usage.json`에 실제 `cache_read_input_tokens`가 쌓이므로, 적중률이 낮으면 나머지를 `EXPLAIN_CACHE=5m` 또는 `EXPLAIN_CACHE=off`로 보내는 판단을 그때 한다(**미측정**).
- 01 문서의 $37보다 높은 이유: 01은 입력 600토큰을 가정했고, 이 프롬프트는 유형별 규칙과 예시 때문에 접두부가 약 4배다. 품질을 위한 선택이고, 샘플 후 줄일 수 있다.
- 샘플 200단어: 동기 호출이라 표준 가격. 첫 요청만 캐시 쓰기, 나머지는 순차 호출이라 캐시 읽기로 계산해 약 $1.7(추정).
- 시간: 배치는 공식 문서 기준 "대부분 1시간 안, 24시간 넘으면 만료". 샘플은 순차 호출이라 건당 지연 × 200인데 지연은 **미측정**(실행 후 출력에 표시됨).

## 7. 검증 규칙 (모델과 무관, `lib/validate.mjs`)

오류 → 재시도 목록, 경고 → 검수표에 표시.

| 규칙 | 등급 | 방법 |
| --- | --- | --- |
| 스키마 | 오류 | 필드 누락·추가·타입·enum을 직접 검사(구조화 출력을 믿지 않음) |
| 예문에 표제어 | 오류 | 아래 "활용 판정" |
| 표제어를 가나로만 씀 | 경고 | 한자 표제어가 읽기로만 나옴 |
| 읽기 정합성 | 오류 | 문장의 가나는 같은 순서로 읽기에 있어야 하고, 한자·숫자 덩어리는 글자당 1~5가나. 가타카나↔히라가나·문장부호는 무시. 읽기에 한자·숫자가 있으면 오류. 표제어 읽기(연탁·촉음화 허용)가 문장 읽기 안에 있어야 함 |
| 로마자 | 오류 | 전각 포함 A–Z. `origin`만 예외 |
| 한국어 필드 | 오류 | 번역·팁·함정·관련어 뜻·훈음에 한글이 있어야 함 |
| 길이 | 오류 | §2 표 |
| 한자 항목 | 오류/경고 | 표제어의 한자만, 중복 없음, 읽기는 가나이고 이 단어의 읽기 안에 있어야 함(오류). KANJIDIC 음훈에 없는 읽기, 훈음의 음절이 Unihan/KANJIDIC 한국음과 다름(두음법칙 허용), 일부 한자 누락은 경고 |
| 유형 | 오류/경고 | 라벨 F인데 `trap` 없음 = 오류. F 아닌데 `trap` 있음, S인데 팁에 가나 없음 = 경고 |
| 관련어 | 오류 | 2~3개, 읽기는 가나, 표제어·그 읽기·표기 변형과 같으면 오류, 서로 중복 오류 |
| 중복 | 오류/경고 | 두 예문이 같음 = 오류. 다른 단어와 예문 공유 = 경고, 출력 전체가 같음 = 둘 다 오류 |
| 부적절 어휘 | 경고 | 짧은 금칙어 목록. 殺す 같은 시험 단어도 있어 자동 거절하지 않음 |
| 단어·태그 변경, 프롬프트 버전 | 오류 | `validate`(·`--stale-prompt`)에서만 |

**활용 판정**: 표제어를 `～`·괄호 주석·`;` 이표기로 나눈 뒤(08 문서 `forms.mjs`와 같은 규칙, 이 폴더에 복사), 각 형태에서 활용 후보를 만든다. 5단 동사는 어간 + 그 행의 가나(書か/書き/書け/書こ, 음편 書い·行っ), 1단 동사는 어간 + ます/ない/て/た/よう 등, い형용사는 어간 + く/かっ/けれ/さ/そう, する동사는 명사+し/さ/せ 또는 명사 단독. **가나 한 글자 어간은 단독으로 맞추지 않아** いる가 아무 い에나 맞는 일을 막는다. `いくら～ても`처럼 가운데 `～`가 있으면 조각이 순서대로 다 있어야 한다. 사전 없는 기계 판정이라 불규칙형(来る의 こない를 가나로 쓴 경우 등)은 놓칠 수 있다 → 재시도 이유에 그대로 남아 사람이 본다. 전체 8,130단어에 "표제어+です" 합성 문장을 넣어 보면 이 판정에서 떨어지는 단어는 0개다(원본 데이터 `いただく/頂く` 뒤바뀜과 5가나 한자 2개를 고친 뒤).

## 8. 검수 절차

01 문서 권고: **출시 전 N5·N4 전수(1,386단어), N3~N1 5% 표본(약 337단어) + 앱 안 신고 기능**, 그리고 전체 생성 전에 **200단어 샘플**(01 §5.5).

1. `run --sample 200` → `review/sample.html`을 읽고 `sample.tsv`의 `verdict`에 ok / fix / regen을 적는다. 특히 볼 것: 예문이 급수에 맞는지, 읽기, 거짓 친구 함정, 훈음, `meaningFlag`.
2. regen이 10% 넘으면 프롬프트를 고치고 PROMPT_VERSION을 올려 샘플을 다시 만든다. 기준 통과 후 전체 실행.
3. 전체 후 `review --levels n5,n4 --all`, `review --levels n3,n2,n1 --share 0.05`. 표본은 급수×유형 칸에 고르게 나누고(같은 명령은 같은 단어를 뽑음), **경고가 있는 항목을 최대 200개 추가**로 붙인다.
4. N3~N1 표본의 regen 비율이 5%를 넘으면 그 급수는 표본을 10%로 늘린다(제안, 01 문서에 없음).
5. regen 판정은 `regen --ids …`, fix는 `accepted/<w+첫 자리>.json`의 `output`을 직접 고친 뒤 `validate`.

작업량(가정: 카드당 30~60초): 샘플 200 + 1,386 + 337 ≈ 1,900카드 ≈ 16~32시간. **미측정.**

## 9. 앱 출력 형식과 로더 계약

**모양**: `data/explain/dist/<묶음 3자리>.json`, 묶음 = `floor(카운터 / 100)`, 카운터 = ID의 `w` 뒤 36진수(`w0k3` → 723 → `007.json`). 급수가 바뀌어도 같은 파일이다.
`{"schemaVersion":1,"from":700,"items":{"<id>":{examples, kanji, tip, trap?, related, origin?}}}` — `meaningFlag`는 빼고 빈 `trap`·`origin`은 생략.
`manifest.json`: `schemaVersion`, `promptVersion`, `generated`(날짜), `models`(모델별 개수), `shardSize`, 급수별 `total/exported/missing(+ID)`, 묶음별 개수·바이트·gzip 바이트, 합계, `credit`.

**왜 이 크기인가**: 급수 하나(N1 2,699단어 ≈ 2MB)를 통째로 받으면 첫 카드가 늦고, 단어마다 파일(8,130개)이면 업로드·캐시 관리가 번거롭다. 100단어 묶음은 82개 파일, 하나에 70~90KB(gzip 30KB 안팎)라 휴대폰에서 단어 하나 보려고 받기에 부담이 없고, 학습 큐는 대개 같은 급수 안에서 돌아 같은 묶음을 다시 쓴다. Worker의 `GET /explain/:wordId`(01 §5.4)는 묶음을 R2에서 읽어 항목 하나만 돌려주면 된다.

**크기 추정**: 손으로 쓴 정상 출력 8개의 앱 형식 평균 642B(측정), gzip 비율 0.39(측정, 표본 작음). 실제 출력은 이보다 길 수 있어 단어당 650~900B로 잡으면 **합계 5.3~7.3MB, gzip 2.1~2.9MB(추정)**. `export`가 실제 바이트를 manifest에 적는다.

**`src/content.ts` 로더 계약 (문서만, `src/`는 수정하지 않음)**

```ts
// explanations: ExplanationSource
// available: manifest를 받았고 manifest.schemaVersion === 1 이며 (유료 권한이 있으면) true
// explanationFor('w1bt'):
//   shard = `${String(Math.floor(parseInt(id.slice(1), 36) / 100)).padStart(3, '0')}.json`
//   묶음은 메모리(+IndexedDB, 07 문서)에 묶음 단위로 캐시. 받기 실패 → reject(화면은 재시도 버튼)
//   item = shard.items[id]; 없으면 null (manifest.counts의 missing — 아직 생성·검수 안 됨)
//   WordExplanation으로 변환:
//     examples = item.examples                         // {ja, kana, ko} 그대로
//     kanji    = item.kanji.map(k => `${k.char}(${k.reading || '—'}) ${k.hanja}`).join(' · ') || (item.origin ?? '')
//     tip      = item.tip
//     related  = item.related.map(({ word, kana, ko }) => ({ word, kana, ko }))
```

제안(다음 단계): `WordExplanation`에 선택 필드 `trap?: string`, `origin?: string`, `kanjiParts?: {char, reading, kind, hanja}[]`를 더해 F 경고 칩과 한자 표를 따로 그린다. 지금 타입으로는 `trap`이 사라진다.

## 10. 단어 하나 다시 만들기

`node cli.mjs regen --ids n4-123` — 기존 결과·실패 기록을 지우고 같은 파라미터로 즉시(동기, 표준 가격, 한 건 $0.02 안팎 추정) 만든다. 검증 실패면 `failed.json`에 이유가 남는다. 이어서 `review --ids n4-123 --all`로 확인하고 `export`. 단어 데이터(`public/data`)나 태그가 바뀐 단어는 `validate`가 알아서 재시도 목록으로 옮긴다.

## 11. 라이선스·출처 표기 (법률 검토 아님)

- **출력물 권리**: Anthropic 상업 약관(2025-06-17 시행판, 2026-11-13 열람)은 "Customer owns its Outputs"라고 하고 Anthropic의 권리를 고객에게 양도한다. 출력으로 경쟁 모델을 학습시키는 것은 금지된다(D.4). 판매용 학습 콘텐츠로 쓰는 데 걸리는 조항은 찾지 못했다.
- **사용자 고지**: 같은 약관 D.3은 출력의 사실 주장을 독립 확인 없이 믿지 말라고 사용자에게 알리도록 요구한다. → 설명 카드 하단에 "AI가 만들고 사람이 검수한 설명입니다. 틀린 곳은 신고해 주세요" 한 줄과 신고 버튼(01 결정 4의 신고 기능과 같은 것). 한국 인공지능 기본법의 생성형 AI 표시 의무가 이 경우(사전 생성·검수된 학습 콘텐츠)에 해당하는지는 **미확인** — 출시 전 01 문서의 전문가 상담 때 함께 묻는다. 표시는 어차피 넣는 것을 권한다.
- **입력 데이터의 라이선스**: 프롬프트에 넣는 한자별 음훈은 `data/hanja/kanji.tsv`(Unihan + KANJIDIC2, CC BY-SA, 08 문서 §1)다. 출력의 훈음·읽기는 사실 정보라 개작물로 보기 어렵다고 판단하지만 **미확인**. 어느 쪽이든 앱 정보 화면에 이미 필요한 EDRDG·Unicode 표기(08 문서)로 충족된다.
- **표기 문안(정보 화면)**: "단어 설명(예문·한자 풀이·팁): Anthropic Claude로 생성, ○○ 검수". manifest의 `credit`에 같은 내용을 둔다.
