# 08. 단어 데이터 파이프라인: 빈도 순서 · 단어 유형 태그

작성 2026-11-13 · 근거 문서: `03-curriculum-dashboard.md` §2.1–2.4, `02-differentiation.md` F2–F4 · 확인일(출처·라이선스) 2026-11-13

## 결론과 추천

1. **빈도 출처는 wordfreq 3.1.1(일본어)로 정했고, 8,130단어 전부에 점수와 급수별 소개 순서를 만들었다.** JMdict(우선순위 태그·"보통 가나 표기"·품사·이표기)를 보조로 써서 동형이의 표기, 옛 오쿠리가나, 동사 활용형 분산을 보정했다. wordfreq 데이터에 한 단어로 직접 맞은 비율은 급수별 91~97%다. 나머지는 복합어 추정이고, 아무 데서도 못 찾은 단어는 5개뿐이다(최저값으로 맨 뒤에 둔다, 버리지 않음).
2. **라이선스 결과: 파생 빈도·순서 데이터는 CC BY-SA 4.0이다.** 상업 앱에 넣어도 되지만 (a) 앱 "정보" 화면과 문서에 wordfreq(OpenSubtitles 등 원출처 포함)와 EDRDG(JMdict/KANJIDIC) 표기가 필요하고, (b) 이 열을 담은 데이터 파일은 CC BY-SA로 배포해야 한다(다른 사람이 가져다 써도 막을 수 없다). 앱 **코드**에는 영향이 없다. 결정 항목 1.
3. **소개 순서는 순수 빈도순이다**(동점이면 JMdict 우선순위, 그다음 ID 순서 = 처음 8,130개는 옛 idx). 단어 유형과 섞지 않는다. 이유는 §2.4.
4. **단어 유형 태그는 4개 필드로 정했다**: `k`(S/F/J/N/M/L/K), `sk`(한국 한자음), `ff`(거짓 친구 설명), `rt`(읽기 유형 on/kun/mix/irr). 03 문서의 S/F/N/L/K에 **J(한국어에 없는 음독 한자어)와 M(혼종)** 을 더하고, "뜻 대신 읽기를 물을지"는 `k === 'S'` 하나로 정한다. `rt`는 F4 한자음 대응 힌트를 켤지 정한다.
5. **기계 사전 작업으로 사람이 볼 몫을 줄였다**: 가나만 쓴 단어 1,199개(L 525, K 674)는 자동 확정, 한자 단어 6,931개에는 한국 한자음 후보(99.8%)와 읽기 유형 후보, 유형 힌트를 붙였다. 한국 한자음은 Unihan `kHangul`(Unicode 라이선스)을 우선 쓰고, 일본 신자체(図·駅·売 등 약 230자)만 KANJIDIC2로 채웠다.
6. **라벨링 키트 완성**: 청크 35개(N5 4 · N4 3 · N3 9 · N2 8 · N1 11, 약 250단어, N5-1은 60단어 시범), 안내서 `data/tags/LABELLING.md`, 검사기 `scripts/enrich/validate-tags.mjs`. 시범 청크 `data/tags/n5-1.json`을 직접 라벨링해 검사기를 통과시켰다.
7. **`build-data.mjs --extras`** 가 기존 4열 뒤에 `o, f, k, sk, ff, rt, a`를 붙인다. **2026-11-13 두 번째 작업에서 8,130단어 전부의 태그를 일관성 규칙으로 정리(§3.4)하고 `public/data/`에 실었다**(`npm run data` = `--extras`). 앞 4열은 바이트 단위로 그대로다.
8. **2026-11-14: 단어 ID를 위치에서 떼어 냈다(§7).** 모든 단어는 `data/ids.json`에 한 번 발급된 안정 ID(`w000`~`w69t`)를 갖고, 앱 데이터는 `public/data/words-n{l}.json` 각 행 맨 앞에 그 ID를 싣는다. 보강 입력(`data/ko`·`data/tags`·`data/freq`·`data/readings`·prepass·`chunks.json`·`reviewed.json`)도 모두 이 ID로 다시 키를 붙였다. 학습자 기록(v3 → v4)과 백업(형식 2 → 3)은 앱이 한 번 옮기고, 옮기기 전 사본을 남긴다.

### 2.2 까다로운 표제어 처리 (`scripts/enrich/forms.mjs`)

- `～`·`〜` 접사: 지우고 남은 부분으로 찾는다(`～匹` → 匹, `お～` → お). 가운데 `～`는 부분을 띄어 찾는다(`いくら～ても`).
- 괄호 주석: 모두 지운다(`(かん)`, `(な)`, `(する)`, `(をつかむ)`, `(はなを～)`).
- 여러 표기: `;` `、` `,` 와 단어 사이 공백으로 나누고 **가장 높은 값**을 쓴다(`丸い; 円い`, `こうよう もみじ`). 여기에 JMdict가 같은 항목·같은 읽기에 등록한 다른 한자 표기도 더한다(옛 오쿠리가나 `終る` → `終わる`, `引っ繰り返す` → `ひっくり返す`).
- 예외 3개는 표로 직접 지정(`×` → ばつ, `〜 (まる) ごと` → 丸ごと, `我`).
- 가나 단어: 가나 그대로 찾는다.

### 2.3 점수 규칙 (`scripts/enrich/freq.py`, 순서대로 시도)

| 코드 | 규칙 |
| --- | --- |
| `w` | 표기(또는 이표기)가 wordfreq에 한 토큰으로 있음. **한자 동사·い형용사는 활용 표면형을 합산**(書く+書か+書き+書け+書こ+書い, する동사 포함). wordfreq는 형태소 표면형을 세므로 이렇게 하지 않으면 동사가 명사보다 체계적으로 낮게 나온다 |
| `h` | `w`인데 같은 표기를 여러 단어가 나눠 씀: 上(うえ/かみ/じょう/うわ), 가나 より(조사/縒り), 낱자 出(出る의 出た). JMdict 우선순위 가중치(공통어 1, 기타 태그 0.3, 없음 0.1, nf01–12는 ×2, 가나로 잘 안 쓰는 한자 단어는 가나 검색 때 ×0.2)로 몫을 나눠 Zipf + log10(몫). 가나 동형어는 영어 뜻과 JMdict 뜻풀이 단어 겹침으로 어느 항목인지 고른다 |
| `c` | MeCab이 여러 토큰으로 나누는 말(何でも, いただきます): wordfreq 합성값에서 토큰 경계마다 0.5, 최대 1.0을 뺀다(wordfreq는 중국어에만 경계당 1을 뺀다) |
| `k` | JMdict가 첫 뜻에 "보통 가나 표기"를 단 단어이고 가나 철자가 다른 흔한 단어와 겹치지 않으면, 가나 철자 빈도가 더 클 때 그 값(唯 → ただ, 沢山 → たくさん) |
| `r` | 표기를 못 찾으면 읽기 빈도 × 0.8(03 문서 규칙). 흔한 동음어가 있으면 쓰지 않음 |
| `j` | 그래도 없으면 JMdict nf 구간의 wordfreq 중앙값(데이터로 보정) |
| `z` | 최저값 Zipf 1.0(f=10) — "wordfreq 목록 하한보다 드묾" |

`r`·`j`는 이표기 보강 뒤 현재 데이터에서 0건이지만 단어 목록이 바뀔 때를 위해 남겼다. 같은 입력이면 같은 출력이다(두 번 실행해 바이트 단위로 같음을 확인).

### 2.4 순서 규칙과 "섞을지" 결정

정렬 키: `f` 내림차순 → JMdict 우선순위(news1/ichi1/spec1/spec2/gai1 = 1, 다른 태그 = 2, 없음 = 3) → ID 순서(`seq`, 처음 8,130개는 옛 idx와 같다) 오름차순. 옛 idx 자체가 고정 시드 셔플이므로 동점 묶음 안은 안정적인 무작위 순서이고, 나중에 추가된 단어는 동점 묶음의 뒤에 붙는다.

**빈도만 쓰고 다른 것과 섞지 않는다.** (1) 03 문서 §2.1의 명세가 이 순서다. (2) 유형(S 먼저 등)과 섞으면 라벨링이 진행될 때마다 순서가 바뀌고, 이미 시작한 사용자의 다음 단어가 흔들린다. S 단어의 값싼 비용은 03 §2.4의 "새 단어 비용" 계수로 하루 계획에서 반영된다. (3) 의미 범주가 몰리는 문제(같은 뜻 연속)는 데이터가 아니라 앱의 큐 규칙(03 §5.2 4번: `ko` 첫 뜻이 같은 단어 연속 금지)이 맡는다. (4) "Zipf×10 정수"로 0.1 단위 묶음이 생기므로 근소한 차이에 과적합하지 않는다.

## 3. 단어 유형 태그

### 3.1 스키마 (`scripts/enrich/tags-schema.mjs`가 기준)

| 필드 | 값 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `k` | `S` 동형동의 한자어 · `F` 거짓 친구 · `J` 일본 한자어(한국어에 없음·드묾·고어) · `N` 고유어(훈독) · `M` 혼종·기타(음훈 혼합·숙자훈·한자+가타카나) · `L` 외래어 · `K` 가나 표기어 | 모든 단어 | 판정 순서: 먼저 "같은 한자 한국어 단어를 알아보는가"(S/F), 아니면 출신(J/N/M), 한자 없으면 L/K |
| `sk` | 한글 음절만, 한자 1자 = 1음절, 두음법칙 적용(접미사 제외) | S·F·J 필수, N·M 선택, L·K 금지 | 한국 한자음(産業 → 산업, 挨拶 → 애찰) |
| `ff` | 한국어 한 줄, 60자 이내, 가나·한자 금지 | F 필수, 그 외 금지 | 뜻 차이(工夫: "한국어 '공부'(학습)와 달리 '궁리·고안'") |
| `rt` | `on` · `kun` · `mix` · `irr` | 한자 있는 단어 필수, 가나 단어 금지 | 읽기 유형. F4 한자음 대응 힌트는 `on`일 때만 |

03 문서와의 차이: **J를 따로 둔다**(N3~N1 한자어의 상당수가 여기 속하고, 뜻 카드가 필요하지만 F 경고는 부적절하며, 음독이라 한자음 힌트는 쓸모 있다). **K는 03과 같은 뜻(가나 표기)**, N은 "한자로 쓴 고유어"로 좁혔다. **"뜻 대신 읽기를 묻는다" = `k === 'S'`** 하나로 판정한다. 그래서 S의 정의를 "한국 성인이 한자를 보고 한국어 단어를 떠올려 뜻을 바로 아는가"로 잡았다(읽기 방식과 무관: 薬 くすり도 S). 읽기 방식은 `rt`가 따로 갖는다. 판정 규칙·예시 33개는 `data/tags/LABELLING.md`.

## 5. 앱 쪽 엔지니어가 알아야 할 것

**행 형식** (`public/data/words-n{l}.json`, 2026-11-14부터): `[id, w, r, ko, en, o, f, k?, sk?, ff?, rt?, a?, x?]` (`x`는 2026-11-14 추가, 11 문서 §5)
- `id`는 안정 단어 ID(§7). **행의 위치는 아무 뜻이 없다**(지금은 ID 순서라 처음 8,130개는 옛 행 순서와 같다). 그 뒤 열은 옛 파일 `n{l}.json`의 행과 열 하나하나까지 같다(`tests/unit/data.test.ts`).
- 옛 파일 `public/data/n{l}.json`(행 `[w, r, ko, en, o, f, …]`, 단어 ID = `<level>-<행 번호>`)은 **동결**했다. 업데이트 뒤에도 열려 있는 옛 버전 탭만 읽는다(§7.4, §7.6).
- `o`(number): 급수 내 소개 순서 0..n−1(순열). `nextNewIds`는 idx 대신 `o` 오름차순으로 고른다. **`o`를 ID로 쓰지 말 것.**
- `f`(number): round(Zipf×10), 10–80. "고빈도 훑기" 같은 기능의 임계값에 쓸 수 있다(예: f ≥ 45).
- 태그 4열은 **라벨링된 단어에만** 있다(지금은 전부). 행 끝의 빈 열은 잘라내므로 행 길이는 6~12이다. 중간의 빈 값은 `''`. 파싱: `src/data.ts parseRow`. `a`는 §3.5. `x`는 S 단어 550개에만 있는 JMdict의 다른 읽기(공백 구분)로, 읽기 카드 오답에서 빼는 데만 쓴다(`data/readings/`, `scripts/enrich/alt-readings.py`, 11 문서).
- `k === ''`(미라벨)은 지금과 같은 뜻 카드로 처리한다. `k === 'S'`만 읽기 전용 카드(03 결정 5: S 정밀도 95% 검수 전에는 켜지 말 것). `k === 'F'`면 빨간 칩 + `ff`. `rt === 'on' && sk`일 때만 한자음 대응 힌트.

## 6. 알려진 약점

- **wordfreq는 표면형 빈도다.** 동형어 보정(h)은 JMdict 태그로 몫을 나누는 근사다. 가나 동형어(とって=손잡이 vs ～にとって), 같은 표기의 다른 읽기(～中 ちゅう/じゅう)는 여전히 부풀거나 같은 값을 받는다.
- 가중치·벌점 상수(0.5/경계, 1/0.3/0.1, ×2, ×0.2)는 결과를 눈으로 보며 정했다. 기준 자료(BCCWJ 등)와 대조해 조정하지 않았다(BCCWJ는 상업 조건 미확인으로 받지 않음).
- 가나로만 쓴 동사(なる, できる)는 활용형을 합산하지 않는다(なら·なっ 같은 표면형이 다른 말과 겹쳐서). 기본형만으로도 충분히 높게 나온다.
- 코퍼스가 자막·웹·SNS 중심이라 회화어가 강하고 신문·시험 문어가 약하다. 데이터는 2021년 스냅숏이다. JMdict는 2021년, KANJIDIC2는 2008년판이다.
- 한국 한자음 후보는 글자별 대표음이라 단어별 관용음(楽 → 악만 있음, 音楽의 '악'은 맞지만 快楽 '락'은 없음)을 놓친다. 라벨러가 고친다.
- 사전 힌트(S/J/N/M)의 정확도는 측정 전이다. `ko`가 모델 번역이라 S 힌트도 그 오류를 물려받는다.
- 라이선스 원문 일부(EDRDG 현재 페이지, unicode.org)는 이 세션에서 직접 열지 못했다(패키지 동봉본·SPDX 사본·검색 결과로 확인).

## 7. 단어 ID (안정 ID, 2026-11-14)

### 7.1 결정: 등록부에서 한 번 발급하는 짧은 ID

**문제.** 이전까지 단어 ID는 `<급수>-<idx>`였고, idx는 원본 CSV를 중복 제거한 뒤 고정 시드로 섞은 위치였다. 단어 하나를 더하거나 빼거나 고치기만 해도 뒤 단어의 위치가 밀려서, 학습자의 카드·북마크·읽기 카드(`:r`)·약한 단어 집계와 보강 파일, 미리 만든 설명이 **소리 없이 다른 단어에 붙는다**(04 QA O4, 07 A-2 #4).

**결정.** 단어마다 ID를 한 번 발급해 `data/ids.json`(등록부)에 적는다. 형식은 **`w` + 36진수 카운터, 최소 3자리**(`w000`, `w0k3`, `w69t`; 4자리부터는 앞자리 0 없음). 카운터는 등록부의 `next`에서만 나오고 커지기만 한다. 한 번 나간 ID는 **바뀌지도, 다시 쓰이지도, 사라지지도 않는다**(지운 단어는 묘비를 남긴다).

| 고려한 것 | 내용 |
| --- | --- |
| 내용 해시(표기+읽기)가 아닌 이유 | 오타를 고치면 해시가 바뀌어 기록이 끊긴다. 같은 표기·읽기가 두 급수에 있는 96쌍(예: 四季 しき가 N3·N2에 각각)은 지금 두 단어·두 카드라 해시만으로는 구별할 수 없다(급수를 넣으면 급수 이동에서 끊긴다). 등록부는 둘 다 해결한다: 고칠 때는 항목의 `w`/`r`/`l`만 고치고 ID는 그대로 |
| 원본 덱의 guid가 아닌 이유 | 같은 guid가 두 급수에 걸린 경우가 30개라 유일하지 않고, 원본 덱이 바뀌면 같이 바뀔 수 있다(우리가 통제하지 못한다) |
| 급수를 ID에 넣지 않은 이유 | 급수를 옮겨도 ID가 그대로여야 한다. 앱은 급수를 ID 문자열이 아니라 같은 빌드가 만든 표(`src/generated/word-ids.ts`, 연속 구간 5개)에서 찾는다 |
| 옛 ID와 겹치지 않는 형식 | 옛 ID(`3-17`)와 새 ID(`w1bt`)는 모양이 달라서, 어느 저장 상태·백업·탭이 쓴 ID든 영원히 구별된다. 옮기는 코드가 이미 옮긴 ID를 다시 옮길 수 없다 |
| 숫자만인 ID를 피한 이유 | `"123"` 같은 키는 자바스크립트 객체에서 정수 키로 맨 앞에 정렬된다. `w`로 시작하므로 카드 객체의 키 순서(=처음 만든 순서)가 옮긴 뒤에도 그대로다 |
| 길이·주소 안전 | 4자(옛 ID 평균 5.4자). `[0-9a-z]`만이라 URL·해시 경로·파일 이름·Batch API `custom_id`에 그대로 쓴다 |
| 백업에서 읽을 수 있는지 | 옛 ID도 위치라 사람이 읽을 수 없었다. 새 ID → 단어는 `data/ids.json` 한 줄로 찾는다 |
| 처음 8,130개의 발급 순서 | N5 → N4 → N3 → N2 → N1, 급수 안은 옛 idx 순. 그래서 `w000` = 옛 `5-0`, 옛→새 대응이 연속 구간 5개로 줄고(앱에 넣는 대응표가 75바이트), 행 순서도 옛 파일과 같다 |

### 7.2 규칙: 단어를 더하고, 빼고, 고치고, 옮기는 법

등록부 한 줄: `"w1bt":{"l":3,"w":"四季","r":"しき","legacy":"3-17"}`. `w`·`r`은 `data/raw/n{l}.csv`의 표기·읽기를 앞뒤 공백만 지운 그대로다. 한 급수 안에서 `(w, r)`은 하나뿐이다(같은 행이 두 번 나오면 첫 행만 쓴다 — 지금 N2 やかん 하나). `legacy`는 안정 ID 이전에 그 단어가 쓰던 위치 ID로, **동결**이다(앱의 일회성 이전이 이것으로 만들어진다).

| 하려는 일 | 할 일 |
| --- | --- |
| 새 단어 | CSV에 행을 넣고 `node scripts/build-data.mjs --assign-ids --extras`. 새 ID가 `next`에서 발급되어 등록부 끝에 붙고, 데이터 파일에서는 그 급수의 맨 뒤에 온다. 보강 입력(ko·freq·tags)을 새 ID로 채운다 |
| 오타 수정(표기·읽기) | CSV와 **등록부 항목의 `w`/`r`을 같이** 고친다. ID는 그대로라 학습 기록이 따라간다. CSV만 고치면 빌드가 멈춘다(아래) |
| 급수 이동 | CSV 행을 옮기고 등록부 항목의 `l`을 고친다. ID·기록 그대로. `order-n{l}.json`은 freq.py로 다시 만든다 |
| 단어 삭제 | CSV에서 빼고 등록부 항목에 `"retired":"<날짜>: <이유>"`를 단다(묘비). ID는 다시 쓰이지 않는다. 학습자 기록은 앱이 격리 보관한다(§7.3) |
| 지운 단어를 되살림 | `retired`를 지운다. 격리됐던 기록이 다음 실행에 돌아온다 |

**빌드가 아무것도 쓰지 않고 멈추는 경우**(`scripts/word-ids.mjs resolve`): ID가 없는 원본 단어(새 단어인지, 고친 단어인지 사람이 정해야 함), 두 등록 항목이 같은 단어를 주장, 원본에 없는데 묘비도 없는 ID(ID는 사라지지 않는다), 묘비가 있는 단어가 원본에 다시 나타남, 모양이 틀린 ID나 `next` 이상인 카운터, 보강 입력에 살아 있는 단어가 아닌 ID, `order-n{l}.json`이 그 급수 ID의 순열이 아님. `--assign-ids`는 새 ID만 발급하고 기존 항목·묘비는 건드리지 않는다.

**고정.** `tests/unit/data.test.ts`가 등록부 전체(8,130 항목)의 sha256, 옛 위치 ID ↔ 단어 대응, `words-n*.json` = 옛 행 + ID, 동결된 `n*.json`의 바이트 sha256, 생성된 `src/generated/word-ids.ts`가 등록부와 같은지를 확인한다. 성질 테스트: 원본 행을 섞어도(40회) 모든 ID가 같고, 단어를 끼워 넣거나 빼도(각 20회) 남은 단어의 ID는 하나도 바뀌지 않으며, 고친 표기·급수 이동은 등록부를 고쳐야만 통과한다.

**한 번만 쓴 스크립트**(감사용으로 남김): `scripts/ids/make-registry.mjs`(옛 파일에서 등록부 발급, 등록부가 있으면 거부), `scripts/ids/rekey-enrichment.mjs`(보강 입력의 idx 키 → ID, 이미 바뀐 파일은 건드리지 않음). 다시 키를 붙인 87개 파일의 값과 순서가 원래와 같음을 확인했다.

### 7.3 앱의 이전 (상태 v3 → v4, 백업 형식 2 → 3)

옛→새 대응표는 `src/generated/word-ids.ts`의 `LEGACY_RUNS`(구간 5개, 75바이트)라서 지연 로딩할 필요가 없다. 모든 경로가 **같은 함수**(`store.ts migrate` → `migrateIds`)를 지난다: 저장된 상태 읽기, iOS 내구 사본 복원(`hydrate`), 백업 가져오기, 가져오기 되돌리기, 옛 탭 기록 합치기.

| 대상 | 처리 |
| --- | --- |
| 카드(`cards`) | 키만 바꾼다(`3-17` → `w1bt`, `3-17:r` → `w1bt:r`). 카드 객체는 그대로 넘겨 FSRS 값이 바이트 단위로 같고, 키 순서도 그대로다 |
| 북마크(`marks`) | 같은 대응. 순서 그대로 |
| 일별 기록(`log`)·XP·설정·`bestE`·저장 카운터(`rev`) | ID가 없어 그대로. `rev`가 이어져서 iOS 사본 비교가 계속 맞는다 |
| 학습 세션·이어 하기·되돌리기 | 따로 저장된 것이 없다(오늘 큐는 카드와 로그에서 다시 계산, 되돌리기는 메모리). 이전 뒤 같은 카드가 같은 순서로 이어진다(e2e로 확인) |
| 약한 단어 | 카드의 `lapses`에서 계산. 같은 단어가 같은 순서로 나온다 |
| 읽기 카드 오답 보기 | 보기를 고르는 시드가 카드 ID 문자열이었다. 같은 보기를 내도록 시드에는 옛 위치 ID를 쓴다(`ids.ts legacySeed`) |
| `kasane.ai.*` | 없어진 AI 기능이 옛 ID로 남긴 캐시. 이전 때 지운다(다시 쓰는 곳이 없음) |
| `kasane.meta` | 백업 알림 날짜뿐이라 바꿀 것 없음 |
| `kasane.state.prev` | 가져오기 되돌리기 사본. 앱은 되돌리기를 메모리 사본으로 하고 저장된 사본을 다시 읽지 않는다. 옛 형식으로 남아 있어도 백업으로 가져오면 같은 함수로 옮겨진다 |
| iOS 내구 사본(`state-a/b.json`) | 첫 저장 때 v4로 바뀐다. 그 전에 옛 사본을 `state-v3-premigration.json`으로 한 번 남긴다 |
| 위젯 | 날짜별 개수만 담아 ID가 없다. 바꿀 것 없음 |
| 모르는 ID | 한 번도 단어를 가리킨 적 없는 옛 ID, 모양이 틀린 키, 이 버전이 모르는 새 ID(더 새 단어 목록·지운 단어)는 **지우지 않고** `orphans`에 그대로 둔다. 화면·집계에서는 빠지고, 백업에 함께 담기며, 그 단어를 아는 버전에서 자동으로 돌아온다. 0개가 아닐 때만 설정 → 데이터에 한 줄로 알린다("이 버전에 없는 단어의 기록 N개도 지우지 않고 함께 보관하고 있어요"). 지금 데이터로는 정상 사용자에게 0개다 |

**안전 보장.**
- **새 키.** v4 상태는 `kasane.state.v4`에 둔다. 옛 상태 `kasane.state.v2`는 이 버전이 **한 번 읽기만 하고 절대 쓰지 않는다** → 그대로 이전 전 사본이 된다(모든 기록 초기화만 지운다).
- **중간에 실패해도 옛 상태가 그대로.** 이전 결과는 `setItem` 한 번으로 저장된다. 저장이 안 되면(용량) 메모리에서 계속 쓰며 기존 저장 실패 경고가 뜨고, 다음 실행에 옛 사본에서 다시 옮긴다. 이전 함수가 예외를 내면 아무것도 쓰지 않고 복구 화면(내보내기·다시 불러오기)을 띄운다.
- **멱등.** 이미 옮긴 상태에 다시 적용해도 바뀌는 것이 없다(새 ID는 새 ID로 남는다). 같은 단어의 옛 카드와 새 카드가 한 상태에 같이 있으면 마지막 복습이 늦은 쪽을 쓰고 다른 쪽은 격리한다.
- **v4 텍스트가 깨졌을 때**는 빈 상태가 아니라 옛 사본에서 다시 옮긴다.
- **용량이 꽉 찼을 때** 포기하는 순서: AI 캐시 → 가져오기 되돌리기 사본(읽는 곳 없음) → 마지막으로 옛 사본(이미 v4에 다 들어 있을 때만, 그것을 비워야 v4가 저장될 때만; 그래도 안 들어가면 옛 사본을 되돌려 놓는다). 학습 기록은 포기하지 않는다. 가장 큰 상태(11,619장)라도 두 사본이 4.7M자로 브라우저 한도(약 5.2M자) 안이다.

### 7.4 여러 탭과 서비스 워커 업데이트

**옛 탭.** 배포 뒤에도 열려 있던 탭은 옛 JS로 돈다. 옛 JS는 `kasane.state.v2`와 `data/n{l}.json`만 알고 둘 다 그대로 있으므로 그 탭은 전처럼 정상 동작한다. 새 키를 읽지도 쓰지도 않으므로 **옮긴 상태를 옛 ID로 덮어쓸 수 없다**(같은 키를 썼다면 옛 탭이 새 ID를 읽다 깨지거나, 새 ID 기록 옆에 같은 단어를 새 단어로 다시 만들었을 것).
그 탭에서 한 공부는 잃지 않는다: 새 버전은 `kasane.state.v2`가 이전 때와 달라졌는지(길이+FNV 지문) 실행할 때와 `storage` 이벤트 때 보고, 바뀌었으면 **카드 단위로 합친다** — 마지막 복습이 더 늦은 카드는 가져오고, 없던 카드·북마크는 더하며, 여기 있는 더 새로운 학습은 되돌리지 않는다. 일별 기록은 필드별 큰 값, XP·`bestE`도 큰 값, 설정은 새 탭 것. 같은 텍스트를 두 번 합쳐도 바뀌지 않는다. 한계: 두 탭에서 같은 날 공부하면 그날 카운트(`c`·`n`)는 둘 중 큰 값이라 적게 셀 수 있고(새 단어를 그만큼 더 받을 수 있음), 옛 탭에서 지운 북마크·초기화·가져오기는 새 탭에 전해지지 않는다(지우는 쪽은 합치지 않는다 — 안전한 쪽).
새 탭끼리는 예전처럼 `storage` 이벤트로 서로의 저장을 받는다.

**서비스 워커.** `registerType: 'autoUpdate'`라 새 워커가 바로 자리를 잡고 열린 탭을 넘겨받는다(04 O1). 보장:
- **옛 JS + 새 데이터는 생기지 않는다.** 옛 JS가 읽는 `data/n{l}.json`은 동결 파일(바이트 sha256 고정)로 배포에 계속 있다. 새 워커는 이것을 미리 캐시하지 않으므로(`globIgnores`) 옛 탭은 네트워크에서 받고, 오프라인이면 기존 "불러오지 못했어요"가 뜰 뿐 기록은 그대로다.
- **새 JS + 옛 데이터도 생기지 않는다.** 새 JS는 `data/words-n{l}.json`만 읽고, 이 파일은 이 배포부터 있다. 앞으로 단어 목록이 바뀐 뒤 다른 배포의 파일을 받더라도(HTTP 캐시 등) 데이터는 **표시에만** 쓰이고 기록을 바꾸지 않는다: 모르는 ID의 행은 건너뛰고, 빠진 단어는 표시되지 않을 뿐이다. 기록의 ID를 바꾸는 것은 JS 안의 동결된 대응표뿐이다.
- 이 보장은 단위 테스트(`tests/unit/id-migration.test.ts`: 다른 배포의 파일·ID 없는 옛 파일을 읽혀도 상태 객체가 같은 객체)와 e2e(데이터 404 동안 기록 불변, 옛 탭의 쓰기 합치기)로 확인한다.

### 7.5 되돌리기(롤백)

- **이전이 틀렸다고 밝혀지면** 각 기기에 이전 전 사본이 있다: 웹은 `kasane.state.v2`(이 버전은 쓰지 않음), iOS는 그것과 `Library/ruma/state-v3-premigration.json`. 고친 버전은 v4를 버리고 사본에서 다시 옮기면 된다(그 사이 공부는 사본 이후라 v4에서 카드 단위로 합친다 — §7.4의 합치기와 같은 함수). 옛 ID → 단어 대응은 `data/ids.json`의 `legacy`와 동결 파일이 근거다.
- **이전 전 버전으로 코드를 되돌리면** 옛 버전은 `kasane.state.v2`만 읽으므로 **이전 시점의 상태로** 돌아간다(그 뒤 공부는 v4 키에 남아 있지만 옛 버전은 보지 못한다). 그러니 되돌리기는 마지막 수단이고, 다시 앞으로 배포하면 v4가 그대로 쓰이고 옛 키에 쌓인 것은 합쳐진다.
- **백업**은 형식 3(v4)이다. 옛 앱은 형식 3을 "더 새로운 버전"으로 거부한다(잘못 읽지 않는다).

### 7.6 옛 파일·사본을 언제 지우나

- `public/data/n{l}.json`: 옛 탭이 사라지면 필요 없다. 배포 후 몇 주(예: 4주) 뒤 지우고 `vite.config.ts`의 `globIgnores`·`dropLegacyData`와 동결 테스트를 같이 지운다. 그 전에는 지우지 말 것.
- `kasane.state.v2`(이전 전 사본): 지금은 지우지 않는다. 가장 큰 상태에서 실행마다 지문 검사에 21–69ms(4× CPU 감속)가 든다. 결정 항목 5.

### 7.8 서버와 설명 파이프라인

- `server/`: `WORD_ID_PATTERN`이 새 형식이고, 단어 데이터는 `words-n*.json`에서 ID를 그대로 읽는다. 샤드는 `w` + 카운터 첫 자리. 급수는 ID가 아니라 데이터에서 가져온다(이야기 프롬프트의 `level`). 배포·실행된 적이 없어 옮길 데이터는 없다.
- `scripts/explain/`: `custom_id` = 안정 ID, 산출물 `dist/<샤드>.json`(샤드 = 카운터 ÷ 100, 항목 키 = ID)이라 앱은 ID만으로 파일을 안다. 급수가 바뀌어도 같은 파일. 작업 폴더 `accepted/`도 ID 묶음별. 실행된 적이 없어 옮길 데이터는 없다.

### 7.9 확인하지 못한 것

- 실제 iOS 기기에서의 이전(WKWebView localStorage + 내구 사본). 가짜 Capacitor로 단위·e2e만 확인했다.
- 실제 배포에서 서비스 워커 교체 순간의 옛 탭(Playwright는 서비스 워커를 막고 돈다). 옛 탭의 쓰기는 같은 출처의 다른 페이지에서 옛 키에 쓰는 것으로 흉내 냈다.
- Python 보강 스크립트(`freq.py`, `alt-readings.py`, `kanji-table.py`)는 고쳤지만 이 환경에 원본 사전 캐시가 없어 **실행하지 못했다**(문법만 확인). JS 보강 스크립트(prepass, 청크, 검사기, 오답 보고서)는 실행해서 결과가 이전과 같음을 확인했다.
